# What our synthetic match data looks like

Everything the app sees is generated by our own match generator as JSON. There is no video. Referee whistles, bookings, VAR and the crowd are all **events or state records**, the same way a pass or a shot is. The demo "match" (2D pitch + synthetic whistle/crowd audio) is rendered *from* this data, never the other way round.

This builds on [dataset-samples.md](dataset-samples.md) (StatsBomb-style events, DFL-style tracking) and the three-schema contract in [team-split-and-structure.md](team-split-and-structure.md). It adds the officiating and atmosphere pieces that the Attention Engine needs.

## The four streams

| Stream | Rate | What it carries | Who reads it |
|---|---|---|---|
| `event` | when something happens | passes, shots, tackles, **fouls, whistles, cards, VAR, subs, stoppages** | stats engine, agents |
| `tracking` | 10 fps | x/y/speed of 22 players + ball | 2D pitch render, pressure/formation stats |
| `atmosphere` | 1 per second + on change | crowd volume, mood, chants, per-side noise | Attention Engine (ambient cues), audio synth |
| `match_state` | on change | score, clock, cards per team, stoppage reason, ball in/out of play | everyone |

All four share one clock: `t` = seconds since kick-off of the period, plus `period`. Pitch is 105 × 68 m, origin bottom-left, home attacks left to right in the first half.

The Attention Engine adds a fifth, derived, stream: `cue` (what to show/vibrate/hold/skip). That is our output, not input.

## 1. Event shapes

Common envelope (every event has these):
```json
{
  "id": "evt_0412",
  "match_id": "syn_2026_001",
  "period": 2, "t": 1268.4, "clock": "66:08",
  "type": "foul",
  "team": "home", "player_id": "H4",
  "location": [88.1, 30.2],
  "related": ["evt_0411"],
  "source": "generator"
}
```

Officiating and stoppage types (the new part):

```json
// Whistle: its own event. Drives the visual "whistle" cue and the synthetic whistle sound.
{ "type": "whistle", "whistle": {
    "kind": "stop",                // stop | restart | advantage_signal | half_time | full_time | kick_off
    "reason": "foul",              // foul | offside | out_of_play | injury | var_review | goal | end_of_period
    "blasts": 1,                   // 1 = normal, 2 = review/drop-ball, 3 = end of match
    "intensity": "long_loud"       // short | normal | long_loud (long_loud = serious foul / penalty)
}}

// Foul
{ "type": "foul", "foul": {
    "victim_id": "A9",
    "kind": "trip",                // trip | push | holding | handball | high_boot | dissent ...
    "severity": "careless",        // careless | reckless | excessive_force (Laws of the Game wording)
    "in_box": true,
    "advantage_played": false,
    "dogso": false                 // denied an obvious goal-scoring opportunity
}}

// Card
{ "type": "card", "card": {
    "colour": "yellow",            // yellow | second_yellow | red
    "reason": "unsporting_behaviour",
    "player_id": "H4",
    "player_total_yellows": 1
}}

// VAR: one event per phase, linked by review_id
{ "type": "var", "var": {
    "review_id": "var_02",
    "phase": "check",              // check | review | on_field_review | decision
    "incident": "penalty",         // goal | penalty | red_card | mistaken_identity
    "original_decision": "no_penalty",
    "outcome": null                // set on phase=decision: stands | overturned
}}

// Substitution
{ "type": "substitution", "substitution": {
    "off_id": "A11", "on_id": "A19",
    "reason": "tactical",          // tactical | injury | time_wasting
    "formation_after": "4-4-2"
}}

// Set piece / restart
{ "type": "set_piece", "set_piece": { "kind": "penalty", "taker_id": "A9" } }
```

Ordinary play events (pass, shot, tackle, carry, clearance) follow the StatsBomb shape from dataset-samples.md, with `xg` on shots and `related` linking pass → shot.

## 2. Atmosphere (the "sound" made into data)

The generator does not record audio. It computes what the crowd would sound like from the events, with a short lag and decay, and emits it as numbers. The demo audio track is synthesised from these same numbers, so sound and visual cues can never disagree.

```json
{ "stream": "atmosphere", "period": 2, "t": 1269.0,
  "volume_db": 96,                 // ~70 quiet ground, ~85 normal, ~100+ goal/penalty
  "delta_db_5s": +14,              // sudden change = something happened
  "mood": "outrage",               // calm | anticipation | tension | outrage | celebration | jeering | silence
  "dominant_side": "away",         // whose fans are loudest
  "home_share": 0.25,
  "chant": null,                   // e.g. {"name": "generic_club_chant", "side": "home"}
  "events_driving": ["evt_0412"]   // why the crowd is doing this (links back to events)
}
```

How the generator derives it (simple rules, tunable):
- Shot with xG > 0.3 → anticipation ramp in the 2 s before, then celebration or groan.
- Foul in the box with no whistle → **outrage** from the attacking side's fans.
- Card against a team → jeering from the other side.
- VAR check running → **tension**, volume drops ("murmur"), rises sharply on decision.
- Long spell of possession in own half → calm, chants start.

## 3. Match state

```json
{ "stream": "match_state", "period": 2, "t": 1270.1,
  "score": { "home": 1, "away": 1 },
  "ball_in_play": false,
  "stoppage": { "reason": "var_review", "since_t": 1270.1 },
  "cards": { "home": { "yellow": 2, "red": 0 }, "away": { "yellow": 1, "red": 0 } },
  "on_pitch": { "home": 11, "away": 11 }
}
```

`stoppage` is what lets the Attention Engine know it is safe to show richer analysis.

## 6. Why this works for the rules and the concept
- Everything is synthetic and generated by our code, so there is no footage or real-data licensing question.
- Sound is represented as data (`whistle`, `atmosphere`), which is exactly what the concept translates into visuals and vibration.
- `called_on_field: false` plus the atmosphere spike is how the system can show "the crowd thinks that was a penalty" even before the referee acts.
- Every cue keeps a `why` that links back to events, which makes the explanations auditable (helps the "explain" stage and the judging).

## Open choices
- Whether tracking frames are generated physically (simple agent simulation) or interpolated between events. Interpolation is enough for a 2D replay.
- How rich the crowd model is. The rules above are enough for the demo; a small learned model is a stretch goal.

## 7. Could a real system produce these fields? (realism check, Oct 13)

The test for every field: in a real stadium, would it come from a source that exists today? In production this app would not read raw pixels. It would read the same three feeds broadcasters already use: an **official event feed** (logged live by data providers' operators), **optical tracking** (multi-camera player/ball positions), and the **stadium/broadcast audio**. Our generator imitates those feeds.

| Field(s) | Real source | Verdict |
|---|---|---|
| tracking x/y, speed, ball position | optical tracking (or CV on broadcast video, like SkillCorner) | realistic |
| pass, shot, carry, clearance, possession, out of play, goal | event feed, and CV can auto-detect most of them | realistic |
| `xg`, pressure, formation | models on top of events + tracking | realistic (derived) |
| card colour, substitution, set-piece kind | event feed (CV can see a card being shown, but feeds log it) | realistic |
| `whistle` (time, number of blasts, length) | audio: whistle detection is a simple, well-solved signal problem | realistic |
| `whistle.reason` | not in the audio; inferred from the next event (foul, offside, VAR) | derived |
| `foul.kind`, `in_box`, `victim_id` | event feed; `in_box` also from tracking | realistic |
| `foul.severity`, `dogso` | human judgement; feeds don't label it | **drop or mark as model guess** |
| `called_on_field` | derived: foul-like contact with no whistle within ~3 s | derived |
| `var.*` phases and outcome | event feed / league official data (VAR states are logged) | realistic |
| atmosphere `volume_db` | audio level, but broadcast mixes change it | **use relative `crowd_level` 0–1** |
| `delta_db_5s`, `dominant_side` | audio change is easy; side needs stadium mics per stand | realistic with stand mics; mark optional |
| `mood` | audio classifier (cheer / boo / chant / silence) is plausible; finer labels like "outrage" are a model guess | keep, mark as model output with `confidence` |
| `events_driving` | not observable; it's our inference | **move to the interpret stage**, not the raw feed |

### Changes this implies for the schema
1. Every record gets `source`: `tracking` | `event_feed` | `audio` | `derived`. The generator fills it honestly, and derived fields carry `confidence`.
2. Replace `volume_db` with `crowd_level` (0–1, relative to this match's baseline). Keep `delta` on the same scale.
3. Drop `foul.severity` and `dogso` from the raw event. If the explainer wants them, a model estimates them and labels them as estimates.
4. Move `events_driving` and `whistle.reason` out of the raw streams and into the insight schema, so the raw data contains only what a real feed would.

This also makes a good pitch line: "every input field exists in today's stadium feeds; everything clever is in our agents".
