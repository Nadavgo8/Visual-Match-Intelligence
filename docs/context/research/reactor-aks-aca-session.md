# Microsoft Reactor session: "Build AI-powered soccer insights apps with AKS and ACA"

Link: https://www.youtube.com/watch?v=EQ187ohgCbo. First analysed 2026-10-18 from the description and chapters, then checked against the full transcript Nadav pasted the same day. Speech-to-text garbled the model names, so they aren't quoted here.

## What it is
- Official session in the "Inside the Game: Developer Hackathon" Reactor series (https://aka.ms/PremierLeagueHack). Brian Benz (Microsoft) presented it live on Oct 14 2026, about 1 hour.
- He demos his own sample, "football results dashboard" (repo at **aka.ms/football-results-dashboard**). It's a Q&A dashboard over 150 years of men's international results (49,547 matches, 337 team names). The data is the public-domain Kaggle dataset by Mart Jürisoo (martj42), plus World Bank development data for mapping country names. The data isn't in the repo; users download it themselves.
- He says this is inspiration only. He isn't entering, and he has no inside knowledge of judging.

## New things worth taking
1. **"Every answer carries its receipts."** His UI shows a badge on each answer: live/grounded, how many numbers were checked, which model, latency, tokens, estimated cost, and a "what this data can't tell you" caveats box. **For us:** every Attention Engine cue and agent explanation should carry the evidence event IDs it came from (we already have `id`/`related` in our event envelope). An "info" tap shows why the cue fired. This is grounding the judges can see.
2. **Observability:** Application Insights + OpenTelemetry traces, with a trace view inside the app showing each step (POST → model → tool calls). This is cheap and demos well, so include it in the video.
3. **Architecture shape to copy:** one set of images, 3 services (web, insights API, ingest job as an ACA job), blob storage for static data, DuckDB in memory, Foundry project with one model deployment, content filter/alert rule, and a single resource group deployed by a bash/PowerShell script. It all runs locally with Docker Compose first.
4. **No Azure credits are provided.** Build and test locally, deploy late, and use ACA scale-to-zero so the judge link stays cheap through Nov 10.
5. **Out-of-scope refusal + content filter:** the agent politely declines non-football questions. Our Q&A agent should do the same.
6. **Data attribution up front:** he credits sources on the front page. We should label our data "synthetic, generated by our match generator" in the UI and README.

## Their architecture slide ("One set of images, three services, two platforms")
Screenshot posted by Nadav, 2026-10-18.
- **Browser** (allow-listed IPs) → **web** (PUBLIC; server-rendered pages + small JSON API) → HTTP → **insights** (INTERNAL; 9 read-only analytics tools + the AI agent) → keyless → **Microsoft Foundry** (one main model, a slower reasoning model optional).
- **Raw data** (your own Kaggle download) → private Blob → **ingest** (JOB: verify, build, publish a version) → **Curated store** (Parquet + manifest in Blob; DuckDB in memory), which insights reads.
- The same images (same digests) run on AKS or ACA. **Application Insights** gets OpenTelemetry from all three services on both platforms.

## How ours maps onto it
| Their piece | Ours | Difference |
|---|---|---|
| Browser, allow-listed | Fan view (2D pitch replay + cue layer, phone vibration) | Must be **open to judges**: no IP allow-list. Rate-limit the AI endpoints instead. |
| web (public) | **web**: React UI + thin API | Theirs is request/response. Ours **pushes** cues live over SSE or WebSocket (ACA supports both). |
| insights (internal): tools + agent | Split in two: **engine** (match replay clock + stats + Attention Engine, all deterministic) and **agents** (explainer, Q&A, personaliser on Foundry, calling engine stats as read-only tools/MCP) | Our extra part is time. The engine replays a match at 1x–10x and decides live what to surface; theirs only answers on demand. Can start as one service and split later. |
| Foundry, keyless | Same, managed identity | Use a fast model for live phrasing at stoppages; anything slower only for the half-time/full-time recap. |
| Raw Kaggle data | **Our synthetic generator** | No outside data at all, which is the cleanest answer to the rules question he couldn't answer. |
| ingest job: verify, build, publish | **generate job** (ACA job): generate a match, validate against `event.schema.json`, publish a versioned set | Same pattern, and it shows off "synthetic data creativity" (a judging line). |
| Parquet + manifest in Blob, DuckDB | Match JSONL/Parquet + manifest in Blob; DuckDB for Q&A queries; live state in engine memory | **Suggest dropping Event Hubs and Cosmos** from the original team-split plan. Replaying from Blob in-process is simpler, cheaper and enough for a demo. |
| App Insights + OTel | Same | One trace per cue ("event X → score Y → shown as vibration"). This doubles as our "why did this fire" receipt. |
| AKS or ACA | ACA only | Three apps + one job, scale to zero, deployed with `azd`/Bicep. |
