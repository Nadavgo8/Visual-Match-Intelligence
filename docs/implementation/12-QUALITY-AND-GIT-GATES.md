עודכן: 23 באוקטובר 2026. מיועד לשני המפתחים ולכלי הבינה שלהם.

מסמך זה משלים את [תוכנית העבודה](VMI-FINAL-PLAN-F.md), בעיקר סעיפים 8–11. הוא מגדיר איך מסיימים כל branch ואיך עוברים בין השלבים 0–5. דרישות המוצר וחלוקת המשימות נשארות בתוכנית; במקרה של סתירה מול מסמך היסטורי, החלטות התוכנית הנוכחית קודמות, ואת הסתירה מתעדים ומתקנים לפני המימוש הנוגע לה.

## 1. אחריות והגדרת סיום

הבהרת המשתמש מ־23.10.2026 מחליפה את דרישת האישור האנושי שהופיעה בגרסאות קודמות: לאחר בדיקות וסקירת קוד תקינות הסוכן מאשר טכנית וממזג את ה־PR אוטומטית בתוך סשן העבודה, ללא אישור ידני שגרתי מהמשתמש או מהשותף.

| תפקיד | אחריות |
|---|---|
| מבצע המשימה | מימוש ממוקד, בדיקות, תיקון ממצאים ותיעוד |
| שלב סקירת הקוד בסשן | קריאת ה־diff והבדיקות מול הדרישות, תיעוד ממצאים והכרעה על SHA מוגדר |
| הסוכן המנהל | ניהול הענף וה־PR, בדיקות, מיזוג לאחר השערים ואימות main |
| הצוות | תיאום החלטות מוצר וחוזים עמומות שלא הוסמכו; ביקורת נוספת לפי הצורך |

סקירת קוד היא שלב נפרד מהרצת הבדיקות. מתעדים מי כתב ומי סקר, גם אם אותו כלי עשה את שניהם; אין להציג זאת כביקורת עצמאית. הכרעה טכנית אינה אישור אנושי או רשומת GitHub APPROVED בשם אדם אחר. בדיקות ירוקות לבדן אינן סקירת קוד.

משימה גמורה רק לאחר עמידה בתנאי הקבלה, בדיקות עוברות, אפס P0/P1/P2 פתוחים, הכרעה טכנית עדכנית, תיעוד, מיזוג ואימות המצב המשולב. הסטטוסים הם `IN_PROGRESS`, `IN_REVIEW`, `CHANGES_REQUESTED`, `READY_TO_MERGE`, `MERGED_PENDING_VERIFICATION`, `DONE`, `BLOCKED`. בדיקה שלא הורצה אינה PASS. הרשאה שגרתית למיזוג אינה היתר לעקוף כללי שרת, לשנות מוצר שלא הוסמך או להפעיל חיוב.

### 1.1 סיכום העבודה — משימות שלמות ו־commits מפורטים

- כל משימה היא יחידת עבודה בעלת תוצאה ברורה: אבחון, מימוש, בדיקות יחידה ורגרסיה, סקירת קוד, תיקון ממצאים ותיעוד באותו branch ובאותו PR. בדיקות וביקורת מתבצעות גם בין תתי־שלבים לפי B1.
- לא פותחים PR נוסף רק עבור קבוצת בדיקות או כדי להציג כשל. פיצול מוצדק כאשר יש שינוי עצמאי בעל ערך שניתן לבדוק ולמזג בפני עצמו, ומתעדים את הסיבה.
- משימה חדשה מתחילה מ־`main` מעודכן. כאשר המשימה הבאה תלויה בשינוי שטרם מוזג, ממתינים למיזוגו ומבצעים רק עבודה עצמאית מותרת. לא בונים PR על ענף תלוי שלא מוזג.
- תקלה שנמצאה בבדיקה נחקרת תחילה עד להבנת מקורה וניסיון תיקון במסגרת הדרישות. לא מסיקים מכשל יחיד שנדרשת החלטת מוצר. פונים למשתמש רק לאחר בירור שמוכיח כי נדרשת החלטה או התערבות לפי הכללים שאישר.
- הפעולות השגרתיות המאושרות כוללות מימוש, בדיקות, סקירה, תיקונים, commits, push ופתיחת/עדכון PR. לאחר PASS בבדיקות ובסקירה ממזגים אוטומטית בסשן, בלי אישור ידני נוסף ובלי להמציא אישור אנושי.
- גוף commit מהותי מפרט **מה השתנה, למה, כיצד נבדק ומה נשאר פתוח**. אין להסתפק בכותרת כללית.
- התקדמות וראיות נשמרות ב־[לוח העבודה](10-WORK-BOARD.md) וב־[מסמך ההעברה](HANDOFF.md). בפניות למשתמש מתמקדים בהחלטות נדרשות ובתוצאות; אין שאלות שגרתיות “להמשיך?”.

הבקשה העדכנית היא להסדיר ולהפעיל אישור טכני ומיזוג אוטומטיים בסשן, גם עבור PR התיעוד הקיים. אין להתחיל במסגרת זו מימוש מוצר נוסף או לשנות את חלוקת המפתחים.

## 2. שערי העבודה בכל branch

| שער | מתי | מה חייבים לבצע | ראיה שמאפשרת להתקדם |
|---|---|---|---|
| B0 — כניסה | לפני שינוי | מצב Git, בעלים, תלויות, קריאת התוכנית והחוזים; הגדרת התנהגות רצויה ומקרי קצה; ריצת בסיס | מזהה משימה, branch, commit בסיס, תוכנית בדיקות ומצב הבסיס |
| B1 — יחידת עבודה | אחרי כל שינוי התנהגות משמעותי ולפני התחלת תת־שלב תלוי | unit tests ממוקדים, סקירת diff של קוד ובדיקות, בדיקת החוזה ותיקון ממצאים | פקודה ותוצאה, ממצאים והכרעה; אין חובה לבצע commit לכל עריכה |
| B2 — ביקורת branch | לפני הכרעת המיזוג | כל חבילת הבדיקות הקיימת, בדיקות חדשות רלוונטיות, סקירת קוד טכנית ממוקדת כשלים ותיקון | PR עם תוצאות, SHA נבדק, דוח סקירה והכרעה טכנית מתועדת |
| B3 — מוכנות למיזוג | אחרי תיקונים וסנכרון מול `main` | בדיקות מלאות על HEAD המעודכן, בדיקת התאמה לבסיס העדכני, סקירת הקוד שנוסף או השתנה מאז האישור | checks עדכניים ואישור מחודש לאחר שינוי; כל הדיונים נפתרו |
| B4 — אימות מיזוג | אחרי squash merge | בדיקות מלאות על commit המיזוג ב־`main` ו־smoke של הזרימה שהשתנתה | SHA של `main`, תוצאות ואישור שאין רגרסיה; רק אז `DONE` |

ריצת unit tests נדרשת גם בענפי תיעוד, תשתית ותיקונים. בענף תיעוד בלבד אין לכתוב בדיקות מלאכותיות שאינן מגינות על התנהגות: מריצים את הקיימות ובודקים קישורים, פקודות ועקביות. אם הסביבה חוסמת הרצה, הענף יכול לשמש להכנת מסמך או Draft PR, אך אינו עובר B2/B3 עד שיש הרצה מאומתת מקומית או ב־CI על אותו תוכן.

כישלון מחזיר לתיקון באותו ענף. תיקון משנה את ה־SHA ולכן דורש ראיות מעודכנות. אין להשתמש בתוצאה ירוקה של commit ישן, להתעלם מ־collection errors או להתקדם לתת־שלב שתלוי בחוזה שנכשל. במקביל מותר להמשיך משימות עצמאיות שהתלויות שלהן עברו.

## 3. תקן לבדיקות מחמירות ובעלות ערך

### 3.1 מבנה ואיכות של unit tests

- שם הבדיקה מתאר התנהגות ותוצאה. המבנה הוא הכנה → פעולה → אימות. קלט קטן ומפורש עדיף על משחק שלם כשאין בו צורך.
- לכל שינוי לוגי בודקים מסלול תקין, גבולות משמעותיים ומסלול כשל. בודקים פלט ותופעות לוואי רלוונטיות, כולל מה שאסור שיקרה.
- תוצאה צפויה נגזרת מדרישת המוצר או מדוגמה מחושבת עצמאית; אין להעתיק לתוך הבדיקה את אותה נוסחה או אותה פונקציה שבמימוש.
- מתקנים באג עם בדיקת רגרסיה שמדגימה את הכשל לפני התיקון ועוברת אחריו. כאשר אפשר, כותבים קודם את הבדיקה הכושלת; מצרפים את שתי התוצאות.
- משתמשים ב־seed קבוע, שעון נשלט ו־fixtures עצמאיים. אין `sleep` אמיתי בבדיקות יחידה, תלות בסדר בדיקות, שעון קיר או קריאת רשת חיצונית.
- מחליפים גבולות חיצוניים כגון מודל, זמן ותעבורה ב־fakes ממוקדים; משאירים את הלוגיקה הנבדקת אמיתית. שינוי private method לבדו אינו סיבה לשבור בדיקה.
- לא מחלישים assertion, מוחקים בדיקה או מעדכנים snapshot רק כדי לקבל ירוק. שינוי ציפייה חייב להצביע על דרישה או החלטת מוצר מאושרת ולהיבדק בשלב הסקירה הטכנית.
- `skip`, `xfail` או warning חדש מחייבים סיבה ובעלים. בדיקה קריטית שנדחתה חוסמת מיזוג; אין לעטוף כשל ידוע ב־retry כדי להסתירו. סימון `xfail` מוצדק חייב להיות strict כך שגם הצלחה בלתי צפויה תיבדק.
- ריצת בדיקות חייבת לאסוף בדיקות בפועל. אפס בדיקות, שגיאת ייבוא או בחירת marker שאינה מכסה את השינוי אינם הוכחת הצלחה.

### 3.2 שכבות הבדיקה

| שכבה | מה נבדק ב־VMI | מתי |
|---|---|---|
| Unit | מכונת מצבים, קישורים, נוסחאות, סינון זמן, בחירת אירועים, validator | בכל יחידת עבודה; החבילה כולה בכל branch |
| Contract | סכמות, גרסאות, שדות חסרים, מזהים, fixtures של מפיק וצרכן | בכל שינוי חוזה ובכל PR שנוגע בו |
| Integration | מחולל → replay → מנוע, FastAPI, WebSocket, בידוד חדרים, סוכנים מול fakes | בכל PR שנוגע בחיבור; ריצה מלאה לפני מיזוג |
| Frontend | פונקציות זמן ומצב, עדכון פריט קיים, מחיקת מצב ישן, אינטראקציות | בכל שינוי JS; יש להקים harness מתאים ב־D2-01 |
| E2E ובדיקה חזותית | מסך וטלפון באותו משחק, pause/seek, reconnect, תקציר, נגישות | smoke לפי השינוי; מסלול משולב בכל שער שלב |
| ביצועים ועמידות | FPS, פערי זמן, מגבלות תורים, עומס ו־soak | מדידה ממוקדת בשינוי רגיש; הבדיקה המלאה בשלב 4 |
| הערכת מודל | סט השאלות של D2-00, נכונות, זמן, תוויות מקור ואפס עלות | לפני הכרעת מודל ובשינוי מודל/הנחיות משמעותי |

הערכת מודל חי אינה unit test. unit tests לסוכנים עובדים ללא אינטרנט ועם תוצאות מוכתבות. נפילת ספק או מכסה אינן עוצרות את בדיקת הלוגיקה ואינן מפעילות ספק בתשלום.

### 3.3 כיסוי ויכולת לזהות טעות

ב־D2-01 מודדים baseline אמיתי ומקבעים אותו. אלה **ספי יעד להפעלה ב־CI**, לא דיווח על הכיסוי הקיים:

| היקף | כיסוי שורות | כיסוי ענפים לוגיים |
|---|---:|---:|
| לוגיקה עסקית חדשה או שהשתנתה | לפחות 90% | לפחות 85% |
| זמן, `run_id`, סינון עתיד, קישור אירועים ו־validator שהשתנו | לפחות 95% | לפחות 90% |
| קוד קיים בכללותו | אין ירידה מה־baseline שנמדד | אין ירידה מה־baseline שנמדד |

בודקים בנפרד שורות וענפים, וכן כיסוי השינוי ביחס ל־merge base. בשינוי קטן מודדים גם את הפונקציה/הרכיב שהשתנו, כדי ששורה אחת שעברה לא תסתיר מסלול חלופי חסר. אחוז כיסוי לבדו אינו מספיק: כל כלל קריטי בתוכנית דורש מקרה התנהגות מפורש. אין להחריג קובץ עסקי מהמכנה כדי לעבור סף.

`pytest-cov --cov-branch --cov-fail-under` בודק סף כולל ואינו אוכף לבדו את כל הספים בטבלה. ב־D2-01 יש להקים בדיקה שקוראת את דוח הכיסוי ומחשבת את מדדי השורות, הענפים והשינוי בנפרד, ונכשלת על מידע חסר. עד שהבדיקה קיימת, אין לסמן את שער הכיסוי כאוטומטי. [תיעוד pytest-cov](https://pytest-cov.readthedocs.io/en/stable/config.html).

בשינוי קריטי הסוקר בוחר גם טעות אפשרית אחת או יותר ובודק שהבדיקות תופסות אותה: החלפת `<` ב־`<=` בגבול חלון, הסרת בדיקת `run_id`, עיבוד כפילות פעמיים או שימוש בזמן התרחשות במקום זמן מסירה. אפשר לבצע זאת ידנית או בכלי mutation מקומי. מבצעים בעותק מבודד ומחזירים את הקוד התקין; אין להכניס mutation למיזוג. טעות רלוונטית שאינה נתפסת דורשת בדיקה טובה יותר.

אין להעלות אחוזים אוטומטית בכל PR. מחמירים בעקבות פער מוכח, ומוסיפים בדיקה שמגינה עליו בלי לנפח את החבילה בבדיקות כפולות.

## 4. נוהל Code Review

### 4.1 שלושה שלבים משלימים בסשן

1. **סקירה עצמית אחרי יחידת עבודה:** קוראים את כל ה־diff, כולל בדיקות, שינויים בקונפיגורציה ותיעוד. בודקים שאין שינוי לא קשור ושמקרי הקבלה אכן מכוסים.
2. **סקירת AI לפני מסירת branch:** מתחילים מדרישות, diff ובדיקות; מבקשים לחפש תרחיש שמפר את ההתנהגות, ולא רק שיפורי סגנון. מתעדים מי כתב ומי סקר. אפשר להשתמש בשיחה נפרדת של כלי קיים, בלי עלות נוספת; אין דרישה לרכוש כלי או להמציא ביקורת בלתי תלויה.
3. **הכרעה טכנית לפני merge:** שלב הסקירה בודק את הקוד והבדיקות, בוחן דוגמה עצמאית ומוודא ראיות. רכיב קריטי דורש גם בדיקה רלוונטית לטעות אפשרית. תוצאת הסקירה היא PASS או חסם מתועד; אין דרישה לקליק של אדם. החלטת חוזה עמומה עדיין דורשת תיאום.

### 4.2 שאלות שהסוקר חייב לכסות

- **נכונות:** האם ההתנהגות עומדת במשימה ובחוזה? מה קורה בקלט ריק, חסר, פגום, כפול או בסדר הפוך? האם התוצאה והמצב עקביים?
- **זמן ובידוד:** האם יש דליפת עתיד, תשובה ישנה אחרי seek/reset, התנגשות בין חדרים או מרוץ בין ביטול לפרסום? האם snapshot נשמר לאורך הבקשה?
- **אבטחה וגבולות:** האם תפקיד הלקוח נבדק בצד השרת? האם קלט ופקודות מוגבלים? האם לוגים או הקוד חושפים סודות? האם שגיאה מפעילה קריאות או עלות בלתי מוגבלות?
- **ביצועים:** האם נוצרים תורים, משימות, caches או נתוני מעקב ללא גבול? האם פעולת AI חוסמת את שעון המשחק? האם משאבים משתחררים אחרי ניתוק?
- **נגישות וממשק:** האם נשמרים סימון יחיד, שני פסים זהים והפרדת אזור המציג? האם המידע ברור גם ללא צבע בלבד ובהפחתת תנועה? האם xG נשאר באפליקציה?
- **איכות בדיקות:** האם assertions היו נכשלים על מימוש שגוי? האם יש מסלול שלילי וגבולות? האם mocks מסתירים את הבאג? האם בדיקות ישנות עדיין מייצגות את התוכנית הנוכחית?
- **תחזוקה:** האם השינוי ממוקד, שמותיו ברורים והחוזה מתועד? האם צריך פחות מורכבות כדי לממש את אותה דרישה?

## 6. שערים בין שלבי התוכנית

לפני כל מעבר שלב הסשן סוקר טכנית את השינויים המצטברים מאז השער הקודם, את החוזים ואת איכות הבדיקות. מריצים את חבילת היחידה והאינטגרציה על **אותו commit משולב ב־`main`**, ומוסיפים את הבדיקות בטבלה. מעבר שלב דורש דוח מעבר והכרעה טכנית מתועדת; PRs ירוקים בנפרד אינם מספיקים.

| יציאה משלב | בדיקות נוספות ותנאי מעבר |
|---|---|
| 0 — בסיס | commit משותף, התקנה ובדיקות על שני מחשבים, fixtures מוסכמים; baseline וכשלי הקמה מתועדים. הכרעת D2-00 נדרשת לפני חיבור AI קבוע, אך אינה חוסמת מסלול עצמאי של מפתח 1 |
| 1 — חתך ראשון | מסירה → בעיטה → תוצאה → xG מאוחר ועצירה → חידוש מופיעים באופן עקבי במסך ובפיד; בדיקה של סדר מסירה שונה, כפילות וללא דליפת עתיד |
| 2 — פיתוח מקביל | כל המפיקים והצרכנים תואמים לאותה גרסת חוזה; fixtures חדשים עוברים בשני המסלולים; המחולל, האווירה והאפליקציה עובדים יחד ללא שינויי חוזה סמויים |
| 3 — מראה ותוכן | מסך 1080p, מסך קטן ומובייל; pause/seek/reset עם בקשת AI ותקציר בתהליך; סמלים ופסים לפי התוכנית; מסלול דמו נגיש ומקור התשובות גלוי |
| 4 — ייצוב | כל מקרי הקצה בסעיף 11 לתוכנית; ≥30FPS; פער שעונים ≤500ms; סימון מקומי ≤250ms אחרי הגעת הקלט הדרוש; שלושה חדרים עם מסך ושני טלפונים בכל חדר; soak של 30 דקות ובדיקת גבולות זיכרון/תורים |
| 5 — הגשה | התקנה/גישה ממחשב נוסף וחלון שאינו מחובר; דמו מלא על SHA ההגשה, בדיקות ירוקות, קישורים וקבצים זמינים, הוראות אנגלית ומגבלות אמת; תרגול התאוששות והכרעה טכנית מתועדת |

לשלב 4 מוסיפים רגרסיה עם רשימת seeds מתועדת: מרחיבים את בסיס `1..20` הקיים ל־`1..100` בבדיקות invariant ממוקדות, בלי לצייר או לשמור את כל הפריימים. מדדי ביצועים נמדדים על חומרה ורשת מתועדות, לפני ואחרי שינוי רגיש, ובמקביל למודל מקומי אם נבחר. אין למדוד latency של סימון כאילו הוא כולל מידע שטרם נמסר.

כשל בשער עוצר רק מעבר שתלוי בו. יוצרים תיקון ורגרסיה, מריצים מחדש את הבדיקה הממוקדת ואת החבילה הרלוונטית, ומחדשים את אישור השער על ה־SHA המעודכן. תיקון אחרי הקפאת יכולות עובר אותו נוהל; אין מסלול hotfix ללא בדיקות וביקורת.

## 7. ניהול Git לשני מפתחים

### 7.1 ענפים, בעלות ותלויות

- `main` הוא הקוד המשותף שניתן להדגים. אין commits או pushes ישירים אליו.
- לכל משימה ענף קצר ו־PR משלה. ברירת המחדל היא שמות ה־`codex/d1-*` ו־`codex/d2-*` שבתוכנית; לתיעוד משתמשים ב־`codex/docs-*`, ולתיקון נפרד ב־`codex/fix-<task>-<topic>`.
- בדיקות, תיקון וריוויו של אותה משימה שייכים לאותו PR. ענף תיקון נפרד מיועד לתיקון עצמאי, למשל לאחר שהמשימה המקורית כבר מוזגה; הוא אינו ברירת מחדל לכל ממצא.
- בענף הקיים `d1-generator-core` לא משנים שם או היסטוריה רק כדי להתאים לדוגמה. מאמתים בעלות, commits ו־PR פתוח לפני שימוש. השמות במסמך הם מוסכמה להמשך, לא הוראה למחוק ענפים קיימים.
- אין צורך בענף `develop` נוסף. מפתחים משימות עצמאיות במקביל ומשלבים מוקדם דרך `main`.
- קובץ או חוזה משותף מקבלים בעלים למשימה; השותף מקבל הסבר ב־PR. שינוי חוזה נפתח ראשון, כולל מפיק, צרכן, fixtures ותאימות. משתמשים במשימות מעבר קטנות כשנדרש; אין למזג מצב ביניים שבור.
- משימה תלויה מתחילה מבסיס משולב שעבר את השער שלה. אם מתחילים שלד עצמאי מוקדם, מתעדים שאינו תלוי בהתנהגות שטרם אושרה.
- לכל מפתח ולכל כלי שעורך במקביל תיקיית checkout/worktree נפרדת. מתעדים משימה, branch, תיקייה וקבצים משותפים כדי למנוע דריסה.

### 7.2 רצף העבודה

הפקודות הן דוגמאות להרצה מתוך שורש הריפו ב־PowerShell. לפני החלפת ענף מאמתים שאין שינויים לא קשורים; שומרים אותם בענף שלהם בלי למחוק או להכניס אותם ל־commit הנוכחי.

```powershell
git status --short
git branch --show-current
git remote -v
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c codex/d1-generator-scenarios
```

השם האחרון הוא דוגמה למשימה D1-02 בלבד. מאמתים שהוא פנוי ובוחרים את הענף של המשימה בפועל. כישלון `pull --ff-only` דורש בירור divergence, לא reset אוטומטי. בתחילת B0 מריצים את חבילת הבסיס לפני שינוי.

במהלך העבודה מבצעים commits קטנים עם מטרה ברורה. מוסיפים קבצים מפורשים; בודקים גם את מה שנכנס ל־staging:

```powershell
git -c core.whitespace=blank-at-eol,blank-at-eof,space-before-tab,cr-at-eol diff --check
git diff
git add docs/implementation/12-QUALITY-AND-GIT-GATES.md
git -c core.whitespace=blank-at-eol,blank-at-eof,space-before-tab,cr-at-eol diff --cached --check
git diff --cached
git commit -m "docs: define review, test and Git quality gates"
git push -u origin HEAD
```

דוגמת ה־commit היא לתיעוד בלבד; בוחרים קבצים והודעה לפי המשימה. אין להוסיף סודות, לוגים, artifacts כבדים או שינויים של השותף. אין להדפיס ערכי credentials לצורך בדיקתם. לאחר push יוצרים PR וממשיכים לשלב הבדיקות והסקירה בסשן. הגדרת `cr-at-eol` היא לפקודת הבדיקה בלבד: חלק מהמסמכים הקיימים שמורים ב־CRLF, ולכן מכירים בסיום השורה של Windows וממשיכים לבדוק רווחים מיותרים בלי לשנות הגדרות Git או לנרמל קבצים לא קשורים.

לפני B3 מסנכרנים **את ענף המשימה הפעיל**:

```powershell
git fetch origin
git merge origin/main
git -c core.whitespace=blank-at-eol,blank-at-eof,space-before-tab,cr-at-eol diff --check
git log -1 --format=%H
```

לאחר הסנכרון מריצים את החבילה המלאה ומעדכנים את הראיות. אין rebase של ענף שהשותף משתמש בו, force push, `reset --hard`, מחיקת עבודה או פתרון התנגשויות אוטומטי לפי “ours/theirs”. שומרים את כוונת שתי הגרסאות ומוסיפים בדיקה לתוצאה המשולבת. אם ההכרעה משנה התנהגות שלא הוגדרה, מתאמים אותה לפני מיזוג.

סדר מיזוג: חוזים ושינויים שמאפשרים תאימות → מפיקים וצרכנים מתואמים → ממשק → ייצוב. ממזגים PR אחד בכל פעם ב־squash, מאמתים את `main`, ורק אז ממזגים PR תלוי נוסף. שינוי ב־`main` אחרי אישור דורש אימות מחודש של ההתאמה והבדיקות; קונפליקט שנפתר דורש ביקורת מחודשת של הפתרון.

### 7.3 מסלול אישור ומיזוג אוטומטי בסשן

הסוכן מבצע את המסלול ברצף במסגרת משימה מורשית, ללא בקשת אישור ידני נוספת:

1. מסיים משימה ב־branch וב־PR ממוקדים, מוודא שה־PR אינו Draft ומקבע את ה־HEAD ואת בסיס main.
2. מריץ את כל בדיקות החובה הרלוונטיות, כולל החבילה הקיימת, ומתעד פקודות, סביבה, תוצאות ו־exit codes. אין מיזוג עם כשל, collection error או בדיקת חובה שלא הורצה.
3. מבצע שלב סקירת קוד מול כל ה־diff, הדרישות ואיכות הבדיקות. מתעד זהות הסוקר, SHA, ממצאים והכרעה. מתקן כל P0/P1/P2 ומאמת מחדש לאחר שינוי. שינוי המדיניות עצמה נבדק מול הוראת המשתמש; הסרת חסם אינה הוכחת איכות.
4. בודק checks ודיונים ב־GitHub. check נדרש ממתין או נכשל, Changes requested לא פתור או חסם הרשאה עוצרים את המיזוג. כשאין CI, מציינים זאת ומסתמכים על ראיות מקומיות אמיתיות; רשימת checks ריקה אינה PASS.
5. מוודא מחדש שה־HEAD והבסיס לא השתנו מאז האימות; אחרת חוזר לבדיקה ולסקירה של הגרסה החדשה. ממזג ב־squash עם התאמה ל־SHA שנבדק, ללא `--admin`, force push או עקיפת כללי השרת. אפשר להשתמש ב־`gh pr merge --squash --match-head-commit` לפי [תיעוד GitHub CLI](https://cli.github.com/manual/gh_pr_merge).
6. מאמת שה־PR מוזג, מביא את commit המיזוג ומריץ בדיקות מלאות ו־smoke רלוונטי על main לפני DONE. שומר SHA ותוצאות סיום ברשומת ה־PR ובתיעוד ההעברה הזמין.

זהו תהליך שהסוכן מבצע בתוך הסשן הפעיל. לא הוקם שירות שפועל אחרי סגירת הסשן או workflow שמאשר כל PR ברקע. אין צורך ב־API בתשלום או באסימון של אדם נוסף; אין התחזות לסוקר אחר או אישור אנושי פיקטיבי.

CI והגנות שרת נשארים עבודת D2-01 בכפוף להרשאות ולעלות. אין להחזיר דרישת אישור אנושי שגרתי שהמשתמש ביטל. אם כלל שרת קיים מחייב אישור שאינו ניתן להשלמה, מדווחים את החסם ולא עוקפים אותו. זמינות הגנות תלויה בסוג הריפו ובמסלול, לפי [תיעוד GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

### 7.4 התאוששות והעברת עבודה

אם בדיקת `main` נכשלת אחרי מיזוג: עוצרים מיזוגים תלויים, משחזרים על SHA מדויק, ופותחים ענף תיקון או revert דרך PR. גם revert עובר בדיקות, סקירה והכרעה טכנית מתועדת. אין שכתוב היסטוריה של `main` ואין מחיקת עבודת השותף.

אחרי B4 מוחקים ענף רק כשמאומת שה־PR מוזג, ה־commit קיים ב־`main` ואין עליו עבודה נוספת או worktree פעיל. אין להסיק שענף squash לא מוזג רק מפלט `git branch --merged`; מאמתים גם את ה־PR והקבצים. בתיעוד העברה שומרים SHA, משימה, בדיקות, ממצאים פתוחים והצעד הבא.

## 8. פקודות בדיקה ותוכנית CI

### 8.1 מה אפשר להריץ עם בסיס הפרויקט הקיים

לאחר התקנת התלויות בסביבה מבודדת ותואמת Python 3.12, מפעילים מצב בדיקה מקומי. הפקודות להלן אינן דורשות markers חדשים או התקנת כלי frontend:

```powershell
$env:VMI_OFFLINE = '1'
$env:VMI_WARM_DEMO = '0'
Remove-Item Env:APPLICATIONINSIGHTS_CONNECTION_STRING -ErrorAction SilentlyContinue
python -m pytest tests/test_generator.py tests/test_engine.py -q -ra --strict-markers --strict-config
python -m pytest tests/test_agents.py tests/test_api.py -q -ra --strict-markers --strict-config
python -m pytest tests -q -ra --strict-markers --strict-config
git -c core.whitespace=blank-at-eol,blank-at-eof,space-before-tab,cr-at-eol diff --check
```

בהרצה ממוקדת אפשר לבחור קובץ או test מסוים; לפני מיזוג מריצים את כל `tests`. הבדיקות הנוכחיות מערבבות יחידה ואינטגרציה, ולכן אין לקרוא לכל תוצאות pytest “unit” בלי לסווג אותן. אין להסתמך על `-m unit` לפני רישום markers וסימון הבדיקות בפועל. שגיאה בסימון תיכשל עם `--strict-markers`, כמוסבר ב[תיעוד pytest](https://docs.pytest.org/en/stable/how-to/mark.html).

בסביבת בדיקה ייעודית חוסמים רשת חיצונית בבדיקות יחידה, ומאפשרים רק את התעבורה המקומית שנדרשת בבדיקות אינטגרציה. משתני offline אינם תחליף לבדיקת הגבולות של קוד חדש. אין כניסה לחשבון ענן או הפעלת מודל חי לצורך חבילת היחידה.

### 8.2 מה D2-01 צריך להקים

1. גרסת Python ותלויות נעולות ששני המפתחים מתקינים בסביבה נקייה. בודקים במפורש מדיניות prerelease של Agent Framework; לא מוסיפים flag רחב כפתרון קבוע בלי בחינת הגרסאות. מתעדים את פקודת ההתקנה המדויקת ואת הגרסאות שנבדקו.
2. סיווג ורישום markers ל־unit/contract/integration ובדיקת איסוף שאינה ריקה לכל קבוצת חובה; פקודה מתועדת אחת לחבילה המלאה.
3. כיסוי שורות וענפים, בדיקת השינוי וספים לפי סעיף 3.3; דוח קריא ו־artifact של JUnit וכיסוי. מגדירים baseline בלי לסמן חובות שלא מולאו כירוק.
4. כלי בדיקה לפונקציות JS ולמצב הממשק, במינימום תלויות מתאים ל־vanilla JS הקיים. אין היום `package.json` ואין פקודת frontend build קיימת; בודקים נכסים סטטיים, ומוסיפים build רק אם נוצר צורך אמיתי.
5. בדיקת lint/format ממוקדת ויציבה, ובדיקת type לרכיבים שהוחלט להחיל עליה. שגיאות חדשות חוסמות; אימוץ הדרגתי של קוד ישן מתועד במפורש ואינו מוחבא ב־ignore כללי.
6. workflow שמריץ checks על PRs ל־`main` וגם על pushes ל־`main`, עם הרשאות מינימליות, timeout וגרסאות actions מקובעות. אין `continue-on-error` לדרישות חובה או חשיפת סודות לקוד PR לא מהימן.
7. required checks כגון `python-tests`, `coverage-gate`, `web-tests`, `static-checks`. מפעילים דרישה רק לאחר שה־job קיים ונבדק. workflow לא מדלג על branch תיעוד כך שבדיקה נדרשת תישאר ממתינה לנצח. `skipped` או `neutral` אינם הצלחה מוכחת בנוהל שלנו.
8. בדיקת קבלה למנגנון: בענף בדיקה מכשילים assertion ומוודאים ש־CI ו־merge נחסמים; מתקנים ומוודאים שהבדיקות והביקורת מתחדשות. אין למזג את הכשל ל־`main`.
9. מסלול ריצה ללא עלות נוספת. לא בוחרים runner, שירות סקירה, סריקה או אירוח מחויב. כש־CI לא זמין, אפשר להכין עבודה ולהריץ מקומית, אך אין להציג את האכיפה האוטומטית כאילו פעילה או לעקוף check נדרש.

## 9. שיפור מתמשך בעקבות ממצאים

אחרי כל PR ואחרי כל שער שלב, כלי הבינה והמפתח מתעדים למידה קצרה. המטרה היא לשנות פעולה שתמנע את הכשל הבא:

1. מה היה הפער, ואיך התגלה: בדיקה, ביקורת, דמו או שימוש משולב.
2. למה הבדיקות או הסקירה הקודמות לא תפסו אותו: גבול חסר, mock לא מתאים, חוזה עמום, תוצאה צפויה שגויה או חוסר בידוד.
3. איזו בדיקת רגרסיה נוספה, ואיזו שאלה ממוקדת נוספה לסקירה הבאה של אותו רכיב.
4. מי אחראי לתיקון, מה ה־PR/commit שמוכיח אותו, ובאיזה ענף הבא נבדוק שהכלל אכן מועיל.

ממצא חוזר מפעיל בדיקת שורש רחבה יותר ברכיב ובצרכניו, לא רק תיקון מקומי נוסף. טעות בבדיקה עצמה עוברת ביקורת כמו טעות במימוש. שינוי סף או כלל מתועד ב־PR עם נימוק והכרעה טכנית מתועדת; אין להוריד רף כדי לשחרר שינוי תקוע.

לא משנים בשקט את תוכנית המוצר, בוחרים ספק מודל או מוסיפים תהליך מכביד בעקבות כל הערה. שומרים את הכללים ממוקדים בסיכון שהוכח, ומסירים כפילות רק אם נשמרת אותה הגנה בבדיקה טובה יותר.
